## How I read each criterion
- **R5.1:** For each parsed expense, the shares from `splitExpense` must sum to the amount, and the largest and smallest differ by at most 1. Every sharer must get a share. The shares in the balances must also add up to the total spent.
- **R5.2:** The balances sum to 0, and each equals paid minus share. Each person's paid and share must match an independent calculation: floor of amount over N, with the leftover cents going to the alphabetically first keys.
- **R5.3:** Every payment is a safe integer above 0 between two different people. Applying them leaves everyone at 0. The count is at most `max(k − 1, 0)`, where k is the number of people with a non-zero balance.
- **R5.4:** Two reads of the same text give identical rows, payments, text output and JSON output. For a shuffled line order I only compare balances per person, matched case-insensitively. Row order and the displayed spelling follow first appearance, so they change legitimately. I read "the same payments for the same line order" as applying only when the order is unchanged, so payments are not compared across a reorder.
- **R5.5:** A failing property throws an error that gives the seed, a replay seed (re-running with that seed and `runs` 1 fails again with the same party), the reason, and the smallest party as ledger text. In the contract I check this with a deliberately wrong splitter. The printed party must be 5 lines or fewer and must still fail when re-read as text. "Smallest" means the shrinker finds no smaller failing party by dropping a person, dropping an expense, simplifying a split or reducing an amount. It is not a guaranteed global minimum.

## For the reviewer
- **Shared dependency:** the contract imports `test/gen.js`, which is not frozen. The five property checks are written inside the contract. Only the generator, runner and shrinker are shared. The contract asserts the generator's ranges, the 300-run count and the report format, so weakening `gen.js` should fail the contract. Freezing `test/gen.js` as well would close that gap.
- **Settle bound:** the design admits that greedy settling is not a global minimum. R5.3's `k − 1` bound is the only thing it guarantees, and it holds.
